# 07 — Audit des trois couches (27/07/2026, 19h50)

> Déclencheur : après le correctif de la validation, l'échec de génération persistait
> (« toujours pareil »). Audit demandé sur Flutter, Supabase et LWS.
> Méthode : ne rien supposer, mesurer chaque couche.

---

## Verdict en une phrase

Le correctif de validation **était bon** (18 tests le prouvent), mais l'application Flutter
était **incapable d'afficher la vraie erreur** : le code de traduction des erreurs n'était
jamais exécuté. On ne regardait donc pas le bon symptôme. Trois autres défauts réels ont été
trouvés et corrigés au passage.

---

## Démarche : établir les faits avant de corriger

| Vérification | Résultat |
|---|---|
| Existe-t-il plusieurs copies de l'Edge Function ? | **Non** — une seule, le déploiement visait la bonne |
| Quelle version est en ligne ? | **v52, déployée à 17h39** — donc *après* l'erreur de 17h33 |
| Le message `Block missing field: order` peut-il encore être produit ? | **Non** — cette boucle a été supprimée. Le message vu ne pouvait plus venir du code déployé |
| Le worker LWS reçoit-il des jobs ? | **0 job en file depuis 40 min** → aucune génération n'a abouti, l'échec est bien en amont du rendu |

C'est la troisième ligne qui a orienté l'audit : si le message affiché ne peut plus être
produit par le serveur, alors **l'affichage mentait**.

---

## Défaut 1 (Flutter) — le code de traduction des erreurs était mort ❌→✅

**Le constat.** Dans `smart_whiteboard_provider.dart`, la gestion d'erreur était :

```dart
final response = await client.functions.invoke('whiteboard-generate-storyboard', body: {...});
if (response.status != 200) {
  // ... traduction soignée : insufficient_credits, invalid_json, invalid_storyboard
}
```

**La cause racine, vérifiée dans le SDK** (`functions_client-2.6.4`, ligne 206) :

```dart
if (isSuccessStatus) {
  return FunctionResponse(data: data, status: response.statusCode);
}
throw FunctionException(status: ..., details: data, ...);
```

`invoke()` **lève une exception** dès que le statut n'est pas 2xx. La ligne
`if (response.status != 200)` ne peut donc **jamais** être atteinte : c'était du **code mort**.
Toute erreur tombait dans le `catch (e) { _setError(e.toString()); }`, d'où le vidage
technique de votre capture — et d'où l'impression de « toujours pareil » : **quelle que soit
l'erreur, l'affichage était identique**.

**Le correctif.** La traduction se fait maintenant dans un `on FunctionException catch`, via
une méthode `_messageForError` qui :
- lit `e.details`, en gérant les deux formes possibles (`Map` déjà décodée **ou** chaîne JSON
  brute) ;
- traduit chaque code métier (`insufficient_credits` avec le solde réel, `not_authenticated`,
  `llm_error`, `invalid_storyboard`, `internal_error`) ;
- envoie le **détail technique dans les logs** et un **message lisible à l'écran**.

**Portée.** Ce motif de code mort existe dans **9 autres services** de l'application
(`academia_livekit_service`, `livekit_token_service`, `videoasset_upload_service`,
`video_segment_merge_service`, `livekit_recording_service`, `academia_ai_service`…). Non
corrigés — hors périmètre du Smart Whiteboard — mais **à traiter** : ces services affichent
eux aussi des erreurs brutes au lieu de messages utiles.

## Défaut 2 (Supabase) — la validation, prouvée par 18 tests ✅

La validation a été **extraite dans son propre module** `validate.ts`, ce qui la rend testable
sans démarrer le serveur HTTP, et couverte par `validate_test.ts`.

```
deno test supabase/functions/whiteboard-generate-storyboard/validate_test.ts
ok | 18 passed | 0 failed (1s)
```

Le premier test **reproduit exactement votre panne** :

```
REGRESSION 27/07/2026 : un bloc sans "order" ne fait plus echouer le cours ... ok
```

Les 17 autres verrouillent le reste du comportement : champs de scène complétés, métadonnées
absentes tolérées, type inconnu ramené à `paragraph`, bloc vide écarté, scène vide écartée,
LaTeX retiré des narrations, `key_words` filtrés sur le contenu réel (y compris insensibilité
aux accents), `beat` inconnu retiré, `emphasis_target` hallucinée retirée, `recall` vers le
futur retiré, `transition` en chaîne normalisée, plafonds appliqués par troncature, et
**entrées réellement inexploitables toujours rejetées** — le nettoyage ne doit pas devenir
du laxisme.

**Pourquoi ces tests comptent.** Cette brique a cassé en production. Elle est désormais la
seule du projet à être couverte, et c'est justifié : elle arbitre entre « l'étudiant a son
cours » et « l'étudiant perd ses crédits ».

---

## Défaut 3 (Supabase) — un échec de journalisation faisait échouer une génération réussie ❌→✅

**Le code d'origine**, après la création du projet et la confirmation des crédits :

```typescript
const logSql = `INSERT INTO app.whiteboard_ai_generations (...) VALUES (...)`;
await supabase.rpc('admin_execute_sql', { p_sql: logSql });
```

**Le problème.** Cet appel n'était pas protégé. S'il échouait, l'exception remontait au `catch`
général, qui renvoie `internal_error` **500**. Or à ce stade :
- le projet **est créé**,
- les crédits **sont débités**,
- le storyboard **est valide**.

L'étudiant recevait donc une erreur pour un cours **parfaitement généré**. C'est un candidat
sérieux au « toujours pareil » : l'échec pouvait se produire *après* le succès réel.

**Le correctif.** L'écriture du journal est enveloppée dans un `try/catch` et l'erreur RPC est
vérifiée. Un échec est **journalisé dans la console** et n'interrompt plus rien. C'est
l'application de la règle de dégradation gracieuse à la couche Supabase, où elle manquait.

> ⚠️ **Dette signalée, non corrigée** : ce `logSql` est construit par **interpolation de
> chaînes** et exécuté via `admin_execute_sql`. L'échappement se limite à `'` → `''`. C'est
> fragile par nature ; une insertion via l'API PostgREST (`.from(...).insert(...)`) serait
> paramétrée et supprimerait le risque. À faire lors d'un prochain passage.

## Défaut 4 (Supabase) — la création du projet n'était pas vérifiée ❌→✅

```typescript
const { data: projectData } = await supabase.rpc('whiteboard_create_project', {...});
```

L'erreur était **ignorée**. Si la création échouait, `projectData` valait `null` et la fonction
répondait malgré tout `{ success: true, project_data: null }`. L'application recevait un
succès sans projet — panne silencieuse, déplacée en aval et beaucoup plus difficile à
diagnostiquer.

**Le correctif.** L'erreur est vérifiée ; en cas d'échec les **crédits sont remboursés** et un
code explicite `project_creation_failed` est renvoyé.

## Ce que cet audit apprend sur la méthode

**Un symptôme identique ne signifie pas une cause identique.** L'affichage brut de l'erreur
masquait *toutes* les erreurs derrière le même vidage technique. Tant que ce défaut d'affichage
existait, aucun diagnostic fiable n'était possible — on aurait pu corriger indéfiniment le
serveur sans jamais savoir si ça marchait.

**La leçon opérationnelle** : réparer l'observabilité **avant** de continuer à réparer la
fonctionnalité. C'est ce qui a été fait ici, et c'est pourquoi la prochaine tentative sera,
elle, diagnosticable.

## Prochaine étape

Relancer une génération depuis l'application. Trois cas possibles, désormais **distinguables** :

| Ce que vous verrez | Signification |
|---|---|
| Le cours se génère | ✅ la chaîne fonctionne, la suite (aperçu, mise en scène, son) peut être évaluée |
| « La génération a produit un cours inexploitable » | Le modèle a produit un JSON vraiment inutilisable — le détail précis est dans les logs (`DEBUG-D19-09b`) |
| « Crédits insuffisants : il vous faut X (solde : Y) » | Les remboursements des tentatives précédentes n'ont pas tous abouti — à vérifier en base |

Dans les deux derniers cas, la ligne `DEBUG-D19-09` des logs Flutter donnera le **code et le
détail exacts** — ce qui manquait jusqu'ici.
